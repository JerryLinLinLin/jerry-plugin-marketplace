# Runtime and permissions

Install the plugin through the marketplace. Its launcher invokes `scripts/install.ps1` when the required executable is missing, downloads the exact runtime pinned in `runtime.json`, verifies its checksum, and then starts the MCP. Later starts reuse that installation. A development or offline installation may supply a matching `bin/HyperVControl.exe`. Plugin and runtime versions are independent; a launcher or skill update does not require a new native executable.

The launcher verifies the EXE hash and starts `--elevate`. Starting the MCP server never prompts: without administrator rights, the server answers initialize, tool listing and ping itself. The first tool call shows one UAC prompt and starts a same-user elevated worker; that call and every later one run in the worker until the MCP session ends, when the client closes stdin or the server exits. Concurrent first calls share the one prompt. Declining it returns an `ElevationDeclined` tool error and changes nothing; the next tool call prompts again, so ask the user before retrying. If the worker exits, one call returns `ElevatedWorkerExited` with its exit code and the path of `worker-startup-error.txt` in the data folder, and the next call starts a new worker with a new prompt. A server that already runs as administrator runs tools in-process, without a worker. `hyperv_capabilities` reports which process answered as `process`: `id`, `elevated` and `mode` (`in-process`, `elevated-worker` or `worker-seam`). Do not disable UAC or grant permanent group membership to make a call work.

The worker talks to the server over a private named pipe. Only the current Windows user's SID has access, and both ends verify process IDs. Because a UAC launch starts the worker with the profile environment, the server forwards the client process's `HYPERV_CONTROL_*`, `HYPERV_GUEST_*` and `_NT_SYMBOL_PATH` variables over the pipe before any MCP traffic. For tests, `HYPERV_CONTROL_WORKER=always` with `--elevate` starts the worker with the server's own token instead of UAC, whether or not the server is elevated, and without those variables, which still arrive only over the pipe. Such a worker reports `worker-seam` and has no rights the server lacks; the pipe and its checks are unchanged.

An ordinary account may run the EXE directly when granted the required Hyper-V rights. PowerShell Direct and some host operations require administrator rights beyond Hyper-V inventory access. The UAC worker runs with the same account's elevated token. Entering another administrator's credentials does not satisfy that identity boundary: run the MCP client/server under the intended administrator account instead. A locked or noninteractive host cannot display a console/UAC UI.

Guest credentials are separate from host elevation. `hyperv_credential` verifies them against the running VM, then stores them in Windows Credential Manager. Separate profiles can hold administrator and standard guest accounts. Environment fallback uses `HYPERV_CONTROL_GUEST_USERNAME/PASSWORD`, or `HYPERV_CONTROL_<PROFILE>_USERNAME/PASSWORD`. Never echo passwords. No credentials are bundled with the plugin.

Prefer current Microsoft WinDbg. `hyperv_debugger_discover` reports paths and file versions. `HYPERV_CONTROL_DEBUGGER_DIR` explicitly selects a full engine directory containing `kd.exe`, `cdb.exe`, dependent DLLs and extensions; do not copy just KD. Installed Microsoft.WinDbg MSIX is preferred over legacy Windows Kits. Install/update through Microsoft's documented WinDbg installer or `winget install Microsoft.WinDbg` when needed for the authorized task.
